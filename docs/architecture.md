# System Architecture

## 1. Overview

The application uses a client-server architecture, with a React frontend communicating with a Node.js and Express backend through a REST API.

The backend handles business logic, authentication verification, authorisation, data access and file operations. PostgreSQL stores structured application data, while Cloudflare R2 stores uploaded files and documents.

The system is designed as a multi-tenant SaaS application, allowing multiple construction companies to use the same platform while keeping their business data logically separated.

## 4. System Components

### Frontend

The frontend is a React application written in TypeScript and built using Vite.

It provides the user interface and handles user interactions, form submissions and communication with the backend API.

TanStack Query manages server-state and API interactions, while Zustand manages client-side application state.

The frontend is hosted on Vercel.

### Backend

The backend is built using Node.js and Express with TypeScript.

It exposes REST API endpoints and is responsible for:

- Processing incoming API requests.
- Validating request data using Zod.
- Verifying Firebase authentication tokens.
- Checking company membership and user permissions.
- Applying business rules and application logic.
- Retrieving and updating database records through Prisma.
- Managing file uploads and retrieval through Cloudflare R2.

The backend is hosted on Render.

### Database

PostgreSQL, hosted on Neon, stores the application's structured data.

Prisma acts as the ORM between the backend application and the database. It provides database queries, relationship management and schema definitions.

### Authentication

Firebase Authentication handles user sign-in and identity management on the frontend.

When a user makes an authenticated API request, the frontend supplies a Firebase ID token.

The backend uses Firebase Admin to verify the token and establish the authenticated user's identity before processing the request.

### File Storage

Cloudflare R2 provides object storage for uploaded files and documents.

The backend handles interactions with R2 rather than allowing the frontend to directly access storage credentials.

For document access, the backend checks the user's permissions and retrieves the relevant document metadata from PostgreSQL. It then generates a temporary signed URL that allows the frontend to access the corresponding file in R2.

## 5. Request and Data Flow

A typical authenticated request follows this sequence:

1. The user interacts with the React frontend.
2. Firebase Authentication provides the frontend with an ID token.
3. The frontend sends an HTTPS request to the Express API, including the authentication token.
4. The backend verifies the token using Firebase Admin.
5. The backend identifies the application user and checks their company membership and permissions.
6. The backend processes the request and applies the relevant business rules.
7. Prisma communicates with PostgreSQL to retrieve or update the required records.
8. The backend returns a response to the frontend.

For file operations, the backend also communicates with Cloudflare R2. Where signed URLs are used, the frontend accesses the file using the temporary URL generated by the backend.

## 6. Multi-Tenant Architecture and Access Control

The application uses a shared database architecture with company-level data separation.

Companies share the same database infrastructure, but business records are associated with a company through tenant identifiers such as `companyId`.

Company membership is managed through a separate `CompanyMembership` model. This allows a user to belong to multiple companies, with their role and access determined within each company.

Access control is enforced by the backend. Requests must be authenticated, the user must have an active membership in the relevant company, and the user's permissions must allow the requested operation.

Database queries are scoped to the authorised company to prevent access to another company's records.

## 7. Deployment and Infrastructure

The application is deployed using separate frontend and backend hosting services.

| Component | Hosting / Service |
|---|---|
| React frontend | Vercel |
| Express API | Render |
| PostgreSQL database | Neon |
| Authentication | Firebase |
| File storage | Cloudflare R2 |

The frontend and backend communicate over HTTPS. The backend connects to the database and file storage through their respective service integrations.

## 8. Architectural Considerations

The architecture was designed around several priorities:

- **Tenant isolation:** Company data must remain separated.
- **Access control:** Users should only access functionality and information permitted by their company role.
- **Maintainability:** Frontend, backend and data responsibilities are separated.
- **Data integrity:** Relational constraints and database transactions help protect important business records.
- **Scalability:** A shared multi-tenant architecture provides a foundation for supporting additional companies and users.
- **Security:** Authentication verification and authorisation are handled by the backend rather than relying on frontend restrictions.
